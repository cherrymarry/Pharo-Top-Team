##  Опис завдання (Варіант № 1)
Спроектуйте класи, вказані нижче. У кожному з них визначте метод виведення в потік, методи порівняння, виконання арифметичних дій. Оголошення цих класів розташуйте у окремому пакеті. Інформацію про екземпляри класів задайте в Playground, прочитайте з клавіатури або з файлу. Функціонал класів перевірте за допомогою модульних тестів.

1. **Сутність «працівник»** характеризується такими даними: прізвище, стаж, оплата за годину та мінімальна кількість годин, які він має відпрацювати за тиждень.
   * **Працівник-програміст** додатково пам’ятає кількість насправді відпрацьованих годин. Його зарплата зменшується на 25%, якщо відпрацьовано менше за норму.
   * **Працівник-керівник** працює 40 годин на тиждень, має певну кількість підлеглих, отримує 1% надбавки за кожного з них.
   Оголосіть класи, що моделюють описані сутності. Екземпляри цих класів вміють повідомляти прізвище, стаж, зарплату за тиждень. Порівнюють працівників за величиною заробітної плати.
2. Створіть п’ять різних працівників та занесіть їх у контейнер. Забезпечте можливість вводити в режимі діалогу інформацію про нового працівника і долучати його до колекції інших. Надрукуйте всі елементи контейнера. Знайдіть найоплачуванішого працівника. Чи це програміст? Продемонструйте використання арифметичних операторів. Створіть дві нові колекції, що містять окремо керівників, і окремо програмістів.
3. Продемонструйте зберігання створених об’єктів до файлу (до різних файлів у різних форматах), до бази даних (наявність бази можна імітувати в пам’яті) та завантаження їх з файлу, з бази.

## Журнал робочого процесу 
*13.10.2026 - Ініціалізація проєкту та налаштування зв'язку Pharo з GitHub через Iceberg.
13.10.2026 -Застосування стратегії гілкування: розробка архітектурного фундаменту (клас Worker, змінні, геттери/сеттери, розрахунок зарплати, метод printOn: та методи порівняння) виконувалася у спеціальній гілці feature/worker-class з подальшим створенням Pull Request для командного рев'ю.
*17.10.2026 - В. Огороднік. Написання модульних тестів для класів Programmer та Maneger. Для цього створили тестові класи на основі TestCase і налаштували тестові об'єкти. Для класу ProgrammerTest реалізували 5 тестів, які покривають як базові сценарії, так і граничні випадки. Для ManagerTest розробили 4 тести.У процесі роботи вирішено проблему неоголошених змінних у Pharo за допомогою опції Declare new instance variable та використано Force Commit для обходу попереджень аналізатора. Усі 9 тестів успішно пройшли перевірку в Test Runner (отримано зелений індикатор).
*18.10.2026 - В. Огороднік. Реалізація логіки роботи з колекціями працівників та їхньої фільтрації. На рівні класу Worker (Class side) додано методи для аналізу даних: для пошуку робітника з найвищою тижневою зарплатою, для вибірки працівників із зарплатою вище вказаного порогу, а також для знаходження програмістів, які отримали 25% штрафу за недопрацьовані години. Для детальної перевірки цієї логіки створено новий тестовий клас WorkerCollectionsTest. Тести повністю покривають як стандартну роботу фільтрів, так і крайні сценарії: обробку порожніх колекцій, вибірку за умов, коли жоден робітник не підходить під критерії, виключення менеджерів зі списку оштрафованих, а також випадок, коли кілька працівників мають однакову максимальну зарплату.
Усі розроблені модульні тести успішно пройшли перевірку в Test Runner із повністю зеленим індикатором.  Усі поставлені завдання з розробки класів-спадкоємців, розрахунку зарплат, тестування та обробки колекцій виконано в повному обсязі.
*Труднощі*
*Потрібно було уважно стежити за дужками при розрахунку штрафу 25% у Programmer (формула (base * 0.75)), оскільки Smalltalk виконує вирази суворо зліва направо без звичного математичного пріоритету множення/віднімання.
*Спочатку виникла плутанина з тим, чи зберігають екземпляри класів у тестах свій стан між викликами різних test... методів, через що було важливо правильно переініціалізувати об'єкти в setUp.
*При реалізації selectPenalizedProgrammersIn: важливо було правильно комбінувати перевірку типу через isKindOf: Programmer та умову на години actualHours < minHours всередині одного блоку select:, щоб уникнути помилки MessageNotUnderstood при випадковому попаданні інших об'єктів.
*Зручності/Переваги*
*Робота з колекціями через блоки (select:, detectMax:) виявилася набагато зручнішою, ніж традиційні цикли for чи while. Одна точка в коді робить одразу і фільтрацію, і обробку даних.
*Можливість працювати х  гілками, комітити та вирішувати конфлікти синхронізації (Pull/Push) безпосередньо з робочого простору Pharo позбавляє потреби переключатися в сторонні консолі чи термінали.
*Дуже зручно, що класи Programmer та Manager перевизначають один і той самий метод weeklySalary, але рахують його по-різному. Коли працюєш із колекцією об'єктів Worker, не потрібно писати складні умови для визначення типу робітника — середовище Pharo саме знає, чий метод викликати для кожного елемента.
*Написання тестів для колекцій виявилося дуже швидким, оскільки в OrderedCollection можна легко комбінувати різні об'єкти ієрархії
